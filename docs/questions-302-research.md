## Product behavior / 产品语义

- **Native `item/tool/requestUserInput`:** “Skip this question” marks a draft skip; “Submit with skipped questions” sends remaining answers plus empty lists for explicitly skipped IDs through the original request. “Skip all and submit” resolves that request with all-empty lists. It resumes native handling of that tool call, including when it blocks a Plan turn. It does not stop the turn. An omitted answer or empty string without an explicit skip is still rejected. 已选择的答案可与跳过项一次提交；未提交前只改变表单草稿。
- **Native asynchronous question message:** “End tracking” / “结束追踪” ends **Covro tracking only**, persistently, for selected indexed questions. The hint and recorded result explicitly say no answer is sent. It makes no start/steer/interrupt/respond call and does not append any native user message. The original question remains visible, and the gateway database preserves the disposition. This intentionally adds durability beyond the CLI's local editor removal; it does not advertise a native cancellation capability.
- **Covro attention:** sidebar counts remain counts of pending request/card groups, using the existing convention. A partially handled group still contributes one; another group remains independent. Running/completed task status is independent of asynchronous question attention. All attention snapshots and new notifications apply the persisted disposition.
- **Already handled or expired:** native resolution events and turn/runtime boundaries remain authoritative. Observed synchronous requests are retained as history, but a saved record never restores a live RPC callback. After a cold restart an unresolved old request is shown expired; known externally resolved requests are shown handled without inventing their unknown answers. Covro's own successful structured submissions retain redacted answer/skip history. Secret values are not copied into this history table.
- **MCP elicitation:** its existing native `decline` / `cancel` handling is separate and unchanged. It is not used for `requestUserInput`. Ordinary agent prose is not turned into a question request or cancellation target.

## Persistence and races

DB Schema **10**, migration `0009_question_tracking`, adds `question_tracking` and `question_action_history`. Async identities are `["request_user_input_async", itemId, index]`, scoped to the native thread. Forks have a new thread identity and do not inherit local dispositions; native questions and answers still follow Codex history.

Every dismissal validates ownership, reads native history (including paginated history), merges current observations, and checks exact question identities before atomically saving the requested set. Duplicate operations use the existing durable operation identity; repeated cleanup does not send another native request. Missing questions fail without partially dismissing valid ones. A newly discovered native answer wins over a local dismissal and is displayed as the actual answer.

Structured asynchronous replies claim question IDs durably immediately before dispatch. Competing replies and dismissals are rejected while the reply is in flight. A definite failure releases the claim and preserves the browser draft; uncertain delivery stays unknown and is never replayed automatically or silently labeled skipped. Native correlated answer history remains authoritative. A locally displayed submitted user message or acknowledged RPC without a native history item does not mark the question answered; the card retains receipt-pending status and the sidebar keeps its pending count across reload. This patch does not add a force-clear mechanism for an uncertain answer submission.

The browser disables a card while sending and retains its draft after failure. The gateway independently enforces the claims; hiding controls alone is not the state transition. The local disposition store contains identities and state, not asynchronous answer text. Existing operation recovery controls remain the way to inspect an uncertain submission.

## Actual native CLI verification

Used the installed **0.166.0 CLI**, a Python standard-library PTY and localhost HTTP Responses stub, a new temporary project and `CODEX_HOME`, with no credentials or account inference. No external `codex app-server` was started. The native CLI owned its normal runtime. Neither existing Covro sessions nor global CLI configuration was changed. Source fixtures are described separately below.

The temporary provider used `wire_api = "responses"`, `requires_openai_auth = false`, and zero stream/request retries. `tools.experimental_request_user_input.enabled = true` was explicit. A local model catalog declared `request_user_input_async` support; an empty isolated home without that capability initially returned “tool is not a function”, which is a setup limitation, not evidence that native async questions are unsupported. The synchronous run additionally enabled `features.default_mode_request_user_input = true` and exercised **Default/nonblocking** mode. Plan/blocking routing was reviewed in upstream source and exercised through Covro's protocol fixture, not through account-backed Plan inference.

1. **Async:** local model emitted a two-question call; the next model response was held open. Expanded the actual native editor (`Shift+Left` in this installed keymap), then used its displayed `Ctrl+]` skip. The editor moved from “1 of 2 / Native question one?” to “Native question two?”. Main model request count stayed **2**, and the CLI still displayed Working. Releasing the held model response completed the original task. Native rollout contains one task-start and one task-complete event, the question message, and no user question-reply envelope. Skip did not create a turn or transmit an answer.
2. **Sync partial skip:** native overlay asked two questions. Enter committed `First` on question `a`; on `b`, cleared the default selection with Backspace and submitted. The actual CLI showed “Submit with unanswered questions? / 1 unanswered question”; choosing Proceed produced the following exact tool result in the next model input and native rollout:

   ```json
   { "answers": { "a": { "answers": ["First"] }, "b": { "answers": [] } } }
   ```

   The original task then completed, with **2** main model requests and one task-start/task-complete pair. This verifies empty arrays as unanswered submissions; it does not assign cancellation meaning to empty strings.

A sanitized machine-readable record is in [questions-302-results.json](questions-302-results.json). Full transient requests/rollouts are not checked in because they contain unrelated runtime instruction text. No actual multi-client native app-server deployment or account-backed question inference was launched for this task; cross-client ordering, stale callbacks, uncertain receipts, and restart races are covered by repository tests and upstream source, with that boundary kept explicit.
